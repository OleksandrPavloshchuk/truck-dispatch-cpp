Мені здається, це якраз дуже вдалий момент для такого аудиту: застосунок уже має певну структуру, конфігурацію середовища, PostgreSQL і окремого користувача БД для застосунку, але ще не обросли всі тією кількістю компонентів, через які потім важко зрозуміти, де саме пролізла проблема.

І щодо того, що забуваються деталі Docker та PostgreSQL: це нормально. Мета не в тому, щоб пам'ятати напам'ять усі параметри `docker compose`, нюанси ініціалізації ролей PostgreSQL і синтаксис `psql`. Важливіше розуміти модель безпеки, знати, що перевірити, і мати відтворювану інструкцію. Власне, такий проєкт може стати для тебе не просто вправою з C++, а невеликим практичним кейсом із secure development.

Я б розділив аудит на два запитання:

1. Що вже захищено, а що ще ні?

2. Як міг би діяти зловмисник, якби отримав доступ до різних частин системи?

Другий пункт особливо корисний: замість абстрактного «треба додати безпеку» ти отримуєш конкретні сценарії атак і перевірки, які можна автоматизувати.

## 1. Що вже є і що варто перевірити

Це попередній аудит за описом конфігурації та SQL-скриптів, які ми обговорювали. Самого актуального коду застосунку, усіх прав PostgreSQL і мережевої конфігурації я зараз не бачу, тому розділятиму відомі моменти та те, що ще треба перевірити.

Секрети відокремлені від коду

Паролі винесені в `.env.dev`, а `.env.*` виключені з Git. Це правильний напрямок.

Перевірити: чи не потрапив `.env.dev` до Git раніше, чи не друкуються секрети через `set -x`, логи або повідомлення про помилки.

Окрема роль PostgreSQL для застосунку

`td_app` не повинна використовуватися для адміністрування БД. Це хороший фундамент принципу найменших привілеїв.

Перевірити фактичні права, власників об'єктів і можливість створювати таблиці, ролі або змінювати схему.

Порт PostgreSQL опублікований на хост

Мапінг на кшталт `15432:5432` може відкрити порт на всіх мережевих інтерфейсах хоста, а не лише на `localhost`.

Для локальної розробки краще явно обмежити публікацію: `127.0.0.1:15432:5432`.

Скрипт ініціалізації видаляє об'єкти

`DROP TABLE` і `DROP USER` — не просто налаштування, а потенційно руйнівні операції. До того ж `psql` за замовчуванням може продовжувати виконання після SQL-помилки.

Додати `-v ON_ERROR_STOP=1` та чітко відокремити локальну ініціалізацію від будь-яких сценаріїв роботи зі збереженими даними.

HTTP API та обробка запитів

Потрібно перевірити авторизацію, валідацію DTO, SQL-запити, розмір тіла запиту, відповіді з помилками та поведінку під навантаженням.

Тут поки недостатньо інформації, щоб стверджувати, що конкретна вразливість уже існує.

### Дві тонкощі, які я б не пропустив

1. `ON_ERROR_STOP` важливіший, ніж здається. У твоєму Bash-скрипті `set -e` не гарантує, що `psql` перерветься на першій SQL-помилці. Тому команда має виглядати приблизно так:

Bash

```
psql \
  -v ON_ERROR_STOP=1 \
  -h "$DB_HOST" \
  -p "$DB_PORT" \
  -U "$DB_ADMIN" \
  -d "$DB_DATABASE" \
  -v app_user="$DB_USER" \
  -v app_password="$DB_PASSWORD" \
  -f "$SQL_FILE"
```

Це не усуває помилку в SQL, але не дає скрипту мовчки продовжити напівуспішну ініціалізацію. І окремо: якщо роль `td_app` вже має видані їй права, `DROP USER` може завершитися помилкою через залежності. Тоді подальше виконання без `ON_ERROR_STOP` особливо небезпечне.

2. `GRANT` не дорівнює повній перевірці найменших привілеїв. Ти видаєш `td_app` права `SELECT`, `INSERT`, `UPDATE`, `DELETE` на таблиці. Це розумна початкова політика, але треба перевірити, чи може роль виконувати непередбачені операції, наприклад створювати об'єкти в схемі. Права на послідовності тут теж варто перевірити окремо, коли вони з'являться; наявний `ALTER DEFAULT PRIVILEGES ... ON SEQUENCES` сам по собі не видає прав на майбутні таблиці.

## 2. Як потенційний зловмисник атакував би цей проєкт

Я б не починав з екзотичних атак. Спершу — найкоротші шляхи до даних, облікових даних або контролю над сервісом.

Сценарій A. Зовнішній доступ до PostgreSQL

Пріоритет високий, якщо порт доступний з мережі

1. Зловмисник сканує доступні порти хоста.

2. Виявляє PostgreSQL.

3. Пробує використати слабкий пароль, витік конфігурації або відому вразливість.

4. Якщо входить під `td_admin`, може отримати значно ширші можливості, ніж у разі компрометації `td_app`.

Захист: прив'язка порту до `127.0.0.1` у dev, мережеві правила, сильний окремий пароль адміністратора, перевірка `pg_hba.conf`, відсутність прямого доступу до БД із зовнішньої мережі.

Сценарій B. SQL injection або надмірні права застосунку

1. Зловмисник надсилає спеціально сформоване значення у REST-запиті.

2. Якщо SQL формується конкатенацією рядків, введення може змінити структуру запиту.

3. Виконані запити діють із правами `td_app`.

4. Якщо права широкі, наслідки теж широкі: читання, зміна або видалення даних.

Захист: параметризовані запити через `libpq`, валідація вхідних даних, окремі права на таблиці та негативні тести на SQL injection.

Сценарій C. Витік `.env.dev` або пароля

1. Конфігурацію випадково комітять, копіюють у логи чи додають до архіву.

2. Зловмисник отримує `DB_PASSWORD` або пароль `POSTGRES_PASSWORD`.

3. Якщо порт БД доступний і мережеві правила дозволяють з'єднання, він може спробувати автентифікуватися.

4. Пароль адміністратора дає значно більший ризик, ніж пароль прикладної ролі.

Захист: перевірка Git-історії, секрет-сканер, різні паролі для адміністратора й застосунку, ротація секретів після витоку, заборона їхнього виведення в логи.

Сценарій D. Зловживання самим API

1. Зловмисник надсилає надто багато запитів або надмірно великі тіла.

2. API витрачає пам'ять, CPU чи з'єднання з БД.

3. Сервіс стає недоступним або повільним для інших користувачів.

Захист: обмеження розміру запиту, тайм-аути, ліміти пулу з'єднань, обмеження частоти запитів там, де це доречно, і контрольоване завершення помилкових операцій.

Сценарій E. Небезпечне розгортання або відновлення

1. Розробник запускає скрипт ініціалізації не в тому середовищі.

2. Скрипт видаляє таблиці або роль, необхідні для роботи.

3. Дані втрачаються або сервіс перестає працювати.

Це не обов'язково зовнішня атака — але для безпеки важливо також захищатися від помилок оператора.

Захист: руйнівні операції лише в dev-скриптах, окремі міграції для схеми, резервні копії та перевірка відновлення з них.

## 3. Що я б додав до security checklist

Я б не намагався зробити весь застосунок «захищеним» одним великим заходом. Краще рухатися за етапами й для кожного записати, як довести, що захист працює.

## 4. Окремо про HTTPS

Коли дійдеш до TLS, варто пам'ятати, що це лише один рівень захисту.

Клієнт

Перевіряє сертифікат сервера

HTTPS / TLS

Шифрування, цілісність, автентифікація сервера

Drogon REST API

Авторизація, валідація, бізнес-правила

Репозиторій → PostgreSQL

Параметризовані запити, мінімальні права

Тут є кілька важливих нюансів:

* HTTPS не замінює автентифікацію та авторизацію API. Навіть за ідеального TLS сервер може дозволяти стороннім читати або змінювати дані.

* TLS між клієнтом і API та TLS між застосунком і PostgreSQL — це два окремі питання. Для локального розробницького середовища можна почати з HTTPS для API; для розгортання БД на окремому хості треба окремо визначити захист з'єднання з БД.

* Якщо використовуватимеш власний сертифікат для dev, потрібно налаштувати довіру до нього. Не варто просто вимикати перевірку сертифіката, щоб клієнт перестав скаржитися.

* Приватний ключ сервера не повинен потрапляти до Git або в Docker-образ. Його життєвий цикл, доступ і заміну потрібно продумати окремо.

## 5. Як перетворити це на практичний security review

Я б зробив у репозиторії `docs/security-checklist.md` і для кожного пункту фіксував три речі: загрозу, захисний механізм і тест, який перевіряє механізм.

Наприклад:

Перевірка: прикладна роль не адмініструє БД

Загроза

Компрометація API дозволяє зловмиснику використати його облікові дані для зміни схеми або адміністрування БД.

Захисний механізм

`td_app` має лише необхідні прикладні права; вона не є власником таблиць і не має адміністративних атрибутів.

Тест

* `SELECT` з дозволеної таблиці — успішний.

* `INSERT` у дозволену таблицю — успішний.

* `CREATE TABLE` у схемі — відхилений.

* `CREATE ROLE` — відхилений.

* Підключення до БД під `td_app` з адміністративними правами — неможливе.

Останній пункт про підключення краще сформулювати як перевірку відсутності адміністративних атрибутів, а не як перевірку неможливості підключення: `td_app` якраз повинна мати змогу підключатися до БД і виконувати дозволені операції.

І ще один корисний крок: автоматизуй ці перевірки так, щоб їх можна було запустити після створення чистого середовища. Це перетворює твої сьогоднішні маніпуляції з PostgreSQL на відтворювану процедуру, яку ти не мусиш щоразу тримати в голові.

Мій порядок для наступного етапу: спершу завершити репозиторій і параметризовані запити, потім перевірити права PostgreSQL та негативні сценарії, після цього налаштувати HTTPS, а вже далі — авторизацію API, якщо вона ще не реалізована. Так буде простіше локалізувати проблеми й перевіряти кожен рівень окремо.
